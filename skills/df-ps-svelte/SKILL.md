# Svelte modules with df-svelte

Svelte modules live in `<rootFolder>/presentation/svelte/` (`…/svelte/` below) and come only from `df-svelte`. The modules, their kinds and the rules are those of `df-ps-react`; this skill lists only what differs. The mandatory rules of `df-ps-scaffold` apply here too: an approved work plan before any new file (rule 1), new files only through the CLI or its listed exceptions (rule 2).

## Workflow

1. Read `domain-first.project-structure.config.json`: source root is `project.rootFolder`; Svelte is enabled by `frontend.svelte`; `frontend.svelte.framework` is `svelte` or `sveltekit`, and both use `df-svelte`. Stories use `frontend.svelte.storybookFramework` (`@storybook/svelte-vite` or `@storybook/sveltekit`). A config of an earlier major version (`CONFIG_OUTDATED`): ask the user to run `npx df-upgrade`; never run it yourself. Without the config, tell the user to run `npx df-init`; without Svelte configured, tell them to run `npx df-init --section frontend`. Initialization and configuration belong to the human: do not run `df-init` or edit these settings yourself.
2. A feature that also needs backend work → plan it with `df-ps-plan-feature`; Svelte runs come last in the plan.
3. Choose a module for each piece of UI by "Choosing the module" of `df-ps-react`: page, widget, UI-kit component, shared model (React's shared hook: Svelte has no hooks). Widgets never import each other; the widget type defaults to `with separated ui`.
4. Show the work plan in the format of `df-ps-scaffold/references/work-plan.md` (the frontend block, `df-svelte` runs) and **stop until it's approved**. Details holds the widget type and, for a page move or delete with SvelteKit, whether the route follows.
5. Run the generators with `df-svelte --request` JSON in plan order (shared models → UI-kit → widgets → pages); check each output.
6. Implement ("Implementing"), after the backend and the regenerated API client.
7. Run `npx df-lint` and the project's svelte-check/lint/tests. Report against the plan.

## Running df-svelte

Prefer `npx df-svelte --describe` and `npx df-svelte --request` JSON. The operations and fields are those of `df-react` (`page`, `widget`, `ui-kit-component`, `move-*`, `delete-*`), with `shared-model`, `move-shared-model` and `delete-shared-model` in place of the `shared-hook` ones; `--describe` lists current Svelte modules as `svelteModules` (shared models with kind `model`). For example:

```bash
npx df-svelte --request '{"operation":"widget","name":"cart","widgetType":"separated"}'
```

Generated files and story templates: `references/generators.md`. Previews, overwrite control and JSON results: `df-ps-scaffold` [agent-mode.md](../df-ps-scaffold/references/agent-mode.md). If the CLI cannot run, report the failure and give the user the prepared JSON command. Never hand-write its output.

Moving, renaming and deleting go through df-svelte, never by hand, with an approved plan, exactly as in `df-ps-react` ("Moving and renaming"). With SvelteKit, moving a page can move its route folder (`src/routes/<name>/`: `+page.svelte`, `+page.ts`, `+layout.svelte`…; child routes stay) and so change its URL (`moveRoute`); deleting a page can delete its route (`deleteRoute`). State it in the plan, and ask the user when the request doesn't say.

### Files you may create by hand

Only these (`df-ps-scaffold`, rule 2, exceptions 3–4), for modules generated by df-svelte:

- Widget UI parts: `…/svelte/widgets/<name>/ui/**`. A widget's own logic stays in its `<script>` (`toUIProps`); no model files next to it.
- Support files inside the widget folder or `ui-kit/<name>/`: styles, assets, `*.test.ts`, `*.stories.ts`. A missing UI-kit or widget UI story: exactly from "Story templates" in `references/generators.md`.
- A page stays one `.svelte` file that composes widgets; its `<style>` block lays out its widgets only. Its own state, UI parts or types mean a widget is missing, so generate it.
- SvelteKit route files next to a generated route (`+page.ts`, `+layout.svelte`, `+error.svelte`) for loading and layout; the route's `+page.svelte` only renders the page component.

## Implementing

- Svelte 5 with runes: props through `$props()`, state through `$state`, derived values through `$derived`. Each component exports its props type from `<script lang="ts" module>`.
- Separated UI widget: props → UI props in `toUIProps` of `n-widget.svelte`, rendered as `<NWidgetUI {...toUIProps()} />`; `ui/` stays presentational. Keep it reactive:
  - call `toUIProps()` in the markup only; `const ui = toUIProps()` in `<script>` reads the values once (`state_referenced_locally` warns);
  - local state (`$state`), methods, `$effect`, `getContext`, `createQuery` are declared in the widget's `<script>`; `toUIProps` only returns them: `({ title: props.title, open, toggle })`;
  - heavy computations go to `$derived`: `toUIProps` rebuilds the whole object on any change;
  - no getters, `svelte-ignore` or model files are needed.
- Headless: the same `toUIProps`, reading `rest` of `let { UI, ...rest } = $props()` (it stays reactive); the consumer passes `UI` (a `Component<UIProps>`).
- UI-kit components and shared models (`…/svelte/shared/model/create-<name>.svelte.ts`, `create<Name>`): the same limits as in `df-ps-react` — driven only by props or arguments; no API client, no data loading, no imports from widgets, pages or contexts.
- Stories (`frontend.svelte.storybookFramework`): fill `args` of `Default` with valid props (the generated `// fill required props of …` marks the place; svelte-check fails on empty `args` once a prop is required) and add one story per meaningful state. Keep `meta`, the file name and the title (`UI-kit/N` or `Widgets/N`).
- Talking to the backend: as in `df-ps-react` ("Talking to the backend") — a generated API client first (Orval's Svelte Query `createQuery`/`createMutation` in `<rootFolder>/presentation/svelte/data-layer/orval`, or its typed client in `<rootFolder>/presentation/data-layer`; queries need `QueryProvider` from `…/svelte/data-layer/query-provider.svelte` above them, which SvelteKit's root `+layout.svelte` provides), `import type` of endpoint contracts only without one. SvelteKit `+page.ts`/`+page.server.ts` loads call the client, not bounded contexts.

`npx df-lint` (check `svelte`) reports a widget importing another widget, UI-kit importing widgets, pages or contexts, shared models importing UI-kit, widgets, pages or contexts, and Svelte importing contexts beyond the contract types. Fix every finding.
